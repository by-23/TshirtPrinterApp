# Grill Me — стресс-тест плана

Интервьюируй пользователя по каждому аспекту плана/дизайна, пока не будет общего понимания. Иди по дереву решений, закрывая зависимости по одной ветке за раз.

## Перед грилингом — собрать вводные

**Обязательный pre-flight.** До первого decision-вопроса убедись, что знаешь baseline-контекст. Прыжок в «План A или Б» без вводных = планировать на песке.

Чек-лист вводных:

- **Целевая платформа.** Desktop / mobile (Android/iOS) / console / web. Меняет приоритеты оптимизации (mobile per-camera tax, draw call cost, VRAM budget).
- **Масштаб.** Реальные числа в рантайме: сколько объектов одновременно, какая частота — не абстрактный «scope».
- **Сторонние пакеты в стеке.** UniText vs TMP, R3 vs UniRx, BatchRendererGroup, кастомные шейдер-системы — знай особенности или сделай ресерч до вопросов.
- **Прежние попытки.** Если фича переделывается — что конкретно пробовали и почему не зашло.
- **Жёсткие constraints.** Публичный API, формат конфигов, deadline'ы, performance baseline'ы.

Как собирать:

- Если вводные **видны из контекста или кода** — зафиксируй явно («Цель: Android, 30+ инстансов, UniText в стеке») и переходи к грилингу.
- Если **не видны** — задай 2–4 вводных вопроса **одним** вызовом `AskQuestion` (несколько `questions` в одном call). Это **исключение** из правила «один вопрос за раз» — вводные не decision'ы.
- Если вводная вскрывается **посередине гриллинга** — pre-flight был неполным. **Останови гриллинг, признай упущение, перепланируй.** Не натягивай старые ответы на новый контекст.

Pre-flight всегда дешевле, чем переписывание плана после пропущенного контекста.

## Правила

1. **Один decision-вопрос за раз.** Без «а ещё» и «во-вторых».

2. **Каждый decision-вопрос — через `AskQuestion`.** Один элемент в массиве `questions`:
   - 2–4 варианта; **рекомендуемый — первым**, в `label` добавь `(Рекомендуется)`.
   - Аргументацию вариантов — в `label` (коротко) или в 1–2 строках текста перед вызовом; у `AskQuestion` нет поля `description` у options.
   - Категорию (`Scope`, `Lifecycle`, `API`) — в `title` формы или в начале `prompt`.
   - Пользователь всегда может выбрать «Other» и написать свободный ответ.
   - Если вариантов реально два — ок, два. Не растягивай искусственно.

3. **Адаптируй дерево от ответов.** Следующий вопрос зависит от выбора. Вопрос, потерявший смысл после ответа — не задавай.

4. **Ответ в коде — иди в код, не спрашивай.** Прочитал, выложил факт, следующий вопрос.

5. **Без длинных преамбул.** 1–2 строки контекста (если нужно), затем `AskQuestion`.

6. **Не отвечай за пользователя в «Other».** Other — свободный текст; не предсказывай его содержимое.

## Формат `AskQuestion` (decision-цикл)

```yaml
title: "Scope"                    # опционально; короткая категория
questions:
  - id: scope_boundary
    prompt: "Что входит в первую итерацию, а что явно откладываем?"
    options:
      - id: minimal
        label: "Только высота персонажа (Рекомендуется) — быстрый вертикальный slice, меньше регрессий"
      - id: full_stat
        label: "Все модификаторы стата — единый API сразу, дольше, но без второго прохода"
      - id: hybrid
        label: "Высота + один смежный stat — компромисс scope и переиспользования"
```

Pre-flight (несколько несвязанных вводных) — до 4 `questions` в **одном** call. Decision-цикл — **один** `questions` на call.

## Когда останавливаться

**По умолчанию — не останавливаться рано.** Закрывай категории:

- Scope (что входит / не входит).
- API shape (имена, типы, конфигурация).
- Lifecycle (создание, уничтожение, смена фаз).
- Edge cases (прерывания, повторы, гонки, нули, отрицательные значения).
- Смежные механики (другие модификаторы, источники эффекта, view, сеть).
- Места изменений в коде (системы, порядок в фиче).
- Риски (что сломает, как диагностировать).

Остановка только если:

- Пользователь явно: «всё, достаточно» / «составляй план» / «хватит».
- Все категории закрыты и открытых веток в дереве не видно.

Задача — вытащить неявные предположения **до** плана или кода.

## Спор и сверка

- **Худшее — поддакивать.** Видишь реальную проблему в ответе — поднимай, даже если пользователь не любит возражения. Согласие «для проформы» = провал скилла.
- **Спорь только при реальной проблеме:** противоречие с ресерчем, `.cursor/rules/`, существующим кодом или внутренней непоследовательностью плана. «Мне кажется иначе» — не повод.
- **Сверка между вопросами.** Новый ответ не противоречит коду/правилам/ресерчу? Противоречит — поднимай с **конкретной цитатой или файлом**.
- **Сомневаешься в рекомендации — ресерч**, не угадывай (`WebSearch`, чтение кода, `.cursor/rules/`).
- **Пользователь возразил рекомендации** — обнови mental model; ту же рекомендацию не повторяй.

## Чего НЕ делать

- **Не давай «меню без рекомендации».** Нет рекомендации — подумай, выбери, обоснуй.
- **Не комментируй процесс** («Сейчас Q3», «Сложный вопрос»). Просто задавай.
- **Не нагромождай decision-вопросы в один `AskQuestion`.** Несколько `questions` в одном call — только pre-flight или один логический шаг с несвязанными полями (name + visibility).
- **Не игнорируй контр-аргументы** — обновляй модель и иди дальше.
