# План реализации — Приложение для принта на футболках

> Составлен на основе ТЗ «Приложение для принта» и результатов гриллинга (архитектурные решения зафиксированы ниже).

## Принятые архитектурные решения

| Решение | Выбор |
|---|---|
| Развёртывание | Локальный сервер на каждой точке (мини-ПК) |
| Центральный сервис | Тонкий облачный relay для QR-загрузки, админки и статистики |
| QR-загрузка фото | Режим relay (через центр) **и** режим own-WiFi — переключатель в админке |
| Поведение при потере интернета | Работать по последнему кэшу (fail-open); ИИ-стилизация недоступна без интернета |
| ИИ | Бесплатные решения через интернет; вырезание фона — в браузере, стилизация — Pollinations API |
| Стек | TypeScript fullstack (Node.js + React) |
| Цены | Глобальный прайс + переопределение для конкретной точки |
| Внешний вид UI | **Строго по эталонным макетам** (см. раздел ниже) |

### Правила соответствия макету

1. **Макет — единственный источник правды по внешнему виду.** Логика и API могут отличаться от макета, но компоновка, цвета, типографика, отступы, иконки и состояния кнопок — нет.
2. **Перед сдачей этапа** — визуальная сверка с PNG: открыть макет рядом с реализацией на целевом разрешении (киоск 65", оператор — обычный монитор).
3. **Не упрощать и не «улучшать» дизайн** без явного согласования: тёмная тема, неоновые рамки категорий, розовый акцент, боковые панели, карточки заказов — как на макете.
4. **Каждый новый экран** киоска/оператора сначала сопоставляется с макетом; если макета нет — согласовать с заказчиком до начала вёрстки.

## 1. Стек технологий

**Единый язык — TypeScript** (везде: клиент, точка-сервер, центральный сервер).

| Слой | Технологии | Зачем |
|---|---|---|
| Frontend (киоск + оператор + админка) | React 18 + TypeScript + Vite, TailwindCSS, React Router, Zustand | быстрый touch-friendly UI, единая кодовая база под разные экраны |
| Мультиязычность | react-i18next | готовая i18n, легко добавить RU/KK/EN/ZH |
| Карусель баннера | Swiper.js | автоскролл + свайп из коробки, лицензия MIT |
| Редактор дизайна | Fabric.js | готовый canvas-движок: drag/scale/rotate/flip/текст/стикеры/слои |
| Realtime (заказы у оператора, статус точки) | Socket.IO | WebSocket с автопереподключением, работает и для outbound-соединения точки к центру |
| Удаление фона (ИИ-раздел) | `@imgly/background-removal` | работает **прямо в браузере** (WASM/ONNX), бесплатно, без сервера и лимитов, кэшируется — переживает офлайн |
| Стилизация фото (ГТА/аниме/нуар) | Pollinations.ai API (image-to-image, модели `kontext`/`gptimage`/`nanobanana`) | бесплатный публичный API, есть image-to-image по референс-фото, бесплатная регистрация снимает часть лимитов |
| QR-коды | `qrcode` (сервер) / `qrcode.react` (клиент) | генерация QR на лету |
| Backend точки (point-server) | Node.js + TypeScript + Fastify | лёгкий, быстрый, отличная типизация |
| Автозаполнение каталога — источник 1: Pinterest (Этап 3) | `pin-dl` (CLI, npm) через `child_process` + Playwright (рантайм-зависимость `pin-dl`) | бесплатный self-hosted скрапинг по поисковому запросу; из коробки даёт alt-текст пина, фильтр по разрешению, задержку между запросами — без ключей и оплаты |
| Автозаполнение каталога — источник 2: Giphy Stickers (Этап 3) | Официальный `stickers/search` JSON API | быстрый и легальный (бесплатный API-ключ), без браузера — параллельно с Pinterest заметно ускоряет наполнение галереи |
| Автозаполнение каталога — источник 3: CleanPNG (Этап 3, экспериментально) | `playwright` напрямую (не через `pin-dl`) | best-effort — сайт закрывает скачивание Cloudflare-челленджем, источник просто ничего не находит при блокировке (fail-open), см. риски |
| БД точки | SQLite (`better-sqlite3`) + Drizzle ORM | zero-config, один файл, не нужен отдельный сервис на мини-ПК |
| Композитинг изображений (мокап + чистый дизайн → PNG) | `sharp` | быстрый, готовый, не нужен canvas на сервере |
| Backend центра (central-relay + админка) | Node.js + TypeScript + Fastify, PostgreSQL + Drizzle ORM | тот же ORM что и на точке, единый язык запросов |
| Auth админки | JWT + bcrypt | стандартная связка |
| UI админки | Ant Design (antd) + Recharts | готовые таблицы/формы/графики — не рисуем админку с нуля |
| Загрузка файлов (QR-relay, видео-реклама) | Fastify `@fastify/multipart` | стандартный плагин |
| Монорепозиторий | pnpm workspaces + Turborepo | общий код (типы, i18n, pricing-логика) между всеми приложениями |

Всё — готовые open-source библиотеки, кастомного пишем по минимуму (в основном бизнес-логику: цены, синхронизацию, композитинг заказа).

> **Node.js ≥24 (было ≥20).** Требование `pin-dl` (см. Этап 3) — поднимается `engines` во всём монорепозитории, чтобы не держать две версии Node в обороте.

## 2. Архитектура

**Точка = локальный сервер** (мини-ПК гонит оба монитора и хранит всё локально).  
**Central-relay** — тонкий облачный сервис для:
- админки (открытие/закрытие точек, статистика);
- приёма фото по QR с телефона клиента;
- доставки обновлений каталога на все точки.

```
                         ЦЕНТРАЛЬНЫЙ ОБЛАЧНЫЙ СЕРВЕР (central-relay)
                         - Postgres: точки, админы, сводная статистика
                         - Admin Panel (Ant Design)
                         - QR-upload relay endpoint (для режима "через интернет")
                                   ▲                              ▲
                       outbound WebSocket (точка сама             HTTPS (клиент грузит
                       инициирует, работает без белого IP)        фото по QR с телефона)
                                   │                              │
        ┌──────────────────────────────────────────────────────────────────┐
        │                    ТОЧКА (мини-ПК, локальный сервер)               │
        │  point-server (Fastify) + SQLite + локальные PNG/MP4              │
        │   - хранит: заказы, каталог (кэш), цены, операторов, рекламу      │
        │   - работает офлайн по последнему известному состоянию            │
        │   - режим QR: relay (через центр) ИЛИ own-WiFi (точка раздаёт AP) │
        │              │                              │                     │
        │      Chrome kiosk (монитор 65", клиент)   Chrome (монитор оператора)
        │      localhost:PORT/kiosk                  localhost:PORT/operator│
        └──────────────────────────────────────────────────────────────────┘
```

### Почему так

- **local_server** — вся логика заказа, редактор, печать, каталог дизайнов работают на точке без интернета и без central-relay; мастер-каталог как отдельная центральная сущность не используется — точка сама себе источник правды по каталогу.
- **fail_open_cache** — точка держит закэшированный статус «открыта/закрыта» и цены, синкается когда есть связь.
- **QR: relay + same_wifi** — переключатель `point.upload_mode: 'relay' | 'wifi'` в админке.
- **AI бесплатно** — вырезание фона в браузере, стилизация через Pollinations.
- **Цены** — global + override на точку.

## 4. Ключевые сущности данных

### point-server (SQLite, на точке)

- `point_config`
- `operators`
- `designs` (+ `sourcePinId`/`sourceUrl` для дедупликации при скрапинге Pinterest — Этап 3) — единственный источник правды по каталогу, без синка с central-relay
- `catalog_scrape_state` (по категории: индекс текущей вариации поискового запроса, дата/статус последнего запуска, сколько скачано, последняя ошибка — Этап 3)
- `catalog_scrape_config` (мин. разрешение вкл/выкл + число, размер страницы/буфера, задержка между запросами, макс. запросов в час — Этап 3, редактируется в панели оператора)
- `banner_items`
- `ai_styles`
- `garments` (тип/цвет/размер/ткань)
- `print_size_prices` (маленький/средний/большой)
- `ads_videos`
- `orders` (статус: new → accepted → printing → done, пути к 2 PNG)
- `sync_queue` (очередь для отправки в центр при восстановлении связи)

### central-relay (Postgres, в облаке)

- `points` (имя, логин/пароль оператора, статус open/closed, upload_mode)
- `admins`
- `orders_archive` (агрегация для статистики)
- `upload_sessions` (токен QR-сессии, привязка к точке, TTL)

## 5. Функциональные модули (из ТЗ)

### Основное приложение (киоск)

- Выбор языка: RU / KK / EN / ZH

- Статистика продаж и заказов

## 6. Пошаговый план реализации

### Этап 0 — Скелет проекта (1 спринт)

- Инициализация monorepo (pnpm + Turborepo)
- Общие пакеты: `shared-types`, `i18n`, `ui-kit`
- ESLint / Prettier / TS-конфиги, CI (lint + build)
- Пустой `point-server` (Fastify + SQLite + Drizzle миграции)
- Пустой kiosk-app (Vite + React), связка с point-server

### Этап 1 — Каркас киоска: навигация, язык, баннер

> **Макет:** `docs/ui-mockups/category-select.png` — реализовать **строго по макету**.

- Главная страница (компоновка, цвета, неоновые карточки — как на макете)
- Переключатель языка RU/KK/EN/ZH (react-i18next)
- Карусель «Популярные принты» (Swiper)
- Сетка разделов 2×3 с переходами в разделы
- Нижняя плашка «Выберите категорию»

### Этап 2 — Редактор дизайна (ядро)

> **Макет:** `docs/ui-mockups/editor.png` — реализовать **строго по макету**.

- Интеграция Fabric.js
- Выбор толстовка/футболка, сторона (перед/зад), цвет/размер/ткань
- Инструменты: масштаб, поворот, отзеркалить, текст, шрифты, цвета, стикеры, загрузка фото
- Рендер мокапа (наложение дизайна на превью одежды)

### Этап 3 — Разделы каталога (автозаполнение с Pinterest + доп. источники)

- Мемы / Аниме и Фильмы / Игры — общий грид-галерея → редактор с preset-дизайном
- Надписи / Свой дизайн — чистая одежда + полный редактор
- CRUD каталога живёт **только** в point-server: каталог не синкается из central-relay/админки и центральный «мастер-каталог» не используется — настройки и данные скрапинга живут только на точке

**Область действия автозаполнения:** только категории `memes`, `anime_movies`, `games` (те, что открывают общую галерею, а не редактор напрямую).

**Скрапинг:**

- Библиотека — `pin-dl` (CLI, npm), вызывается из point-server через `child_process`.
- Запрос по умолчанию — `"{категория} png"`; когда уникальные пины по нему исчерпаны — заранее заданные вариации запроса на категорию (например «аниме персонажи png», «anime png», «аниме арт png» и т.п.).
- Задержка между запросами и максимум запросов в час — настраиваемые (защита от блокировки IP точки), см. `catalog_scrape_config`.
- ⚠️ Риск: у Pinterest нет публичного API для поиска — скрапинг идёт в обход их ToS, блокировка IP точки возможна в любой момент независимо от аккуратности реализации; `pin-dl` v0.1.0 — свежая и потенциально нестабильная библиотека.

**Несколько источников (ускорение наполнения):**

Живой Pinterest-скрапинг (headless-браузер внутри `pin-dl`, задержки между запросами) — самое узкое место по скорости: пока он не отдал результат, галерея может подолгу не получать новых картинок. Чтобы карточки появлялись быстрее, `topUpCategory` (`apps/point-server/src/modules/catalog-scraper/scrapeService.ts`) запускает несколько источников **параллельно** (`Promise.allSettled`) — каждый источник пишет найденные дизайны в БД сразу по мере скачивания, независимо от того, сколько ещё работают остальные; страница раздела подхватывает их на ближайшем опросе (см. «Наполнение и подгрузка» ниже), не дожидаясь, пока Pinterest тоже закончит.

Источники живут в `apps/point-server/src/modules/catalog-scraper/sources/` за общим интерфейсом `ScraperSource` (`search()` возвращает уже скачанные на диск файлы — дальше единый пайплайн проверки прозрачности/дедупликации/сохранения, общий для всех источников):

| Источник | Как работает | Риски / ограничения |
|---|---|---|
| **Pinterest** (`pinterestSource.ts`) | `pin-dl` через `child_process`, headless-браузер под капотом | см. риск выше — всегда включён, единственный обязательный источник |
| **Giphy Stickers** (`giphySource.ts`) | Официальный JSON API (`/v1/stickers/search`), обычный `fetch`, без браузера — на порядок быстрее Pinterest | Нужен свой бесплатный `GIPHY_API_KEY` (`.env` точки, developers.giphy.com) — без ключа источник молча ничего не докачивает (fail-open). Стикеры не всегда 1-в-1 попадают в тематику «мемы/аниме/игры» — качество тегов зависит от поисковых фраз в `catalog_scrape_query_tags` |
| **CleanPNG** (`cleanpngSource.ts`) | `playwright` напрямую (без `pin-dl`): страница поиска отдаётся без JS, но сама кнопка «Free Download» закрыта Cloudflare JS-челленджем | ⚠️ Best-effort и рискованно: тот же класс риска, что и Pinterest (обход защиты от ботов, неопределённый статус прав на переразмещённые картинки), при этом **без** выигрыша в скорости — почти всегда просто ничего не находит, когда Cloudflare не пропускает headless-браузер. Каждая неудача проглатывается (fail-open), на общий результат прогона не влияет |

Другие похожие агрегаторы (PNGWing, PNGEgg) отдают 403 уже на поиске; PNGImages.com отдаёт превью, пережатые в JPEG (прозрачность потеряна) — оба варианта отбракованы как неподходящие. Dribbble не рассматривался как источник — это витрина UI/UX-дизайна (макеты интерфейсов), а не мемы/аниме/игровые PNG, и официальный API не даёт скачивать по тегам с фильтром по прозрачности.

Источники Giphy/CleanPNG включаются/выключаются независимо в панели оператора («Настройки автозаполнения» → `catalog_scrape_config.giphyEnabled`/`cleanpngEnabled`, оба по умолчанию `true`); Pinterest отключить нельзя.

**Валидация и дедупликация:**

- После скачивания — проверка альфа-канала через `sharp`; если фон не прозрачный (обычный белый/чёрный подложка или фото) — картинка отбрасывается, берётся следующий кандидат из выдачи (фон **не** дорисовывается через `@imgly/background-removal` — не тот компромисс качество/скорость). Источники не-Pinterest (Giphy/CleanPNG) дополнительно всегда перекодируются в настоящий PNG через `sharp(...).png()` перед проверкой — их «родной» формат (GIF/WebP-стикер, скачанный по прямой ссылке) не гарантированно `.png` по расширению.
- Дедупликация — по паре «источник + ID» (`designs.sourcePinId`, значение вида `pinterest:123` / `giphy:abcXYZ`; без perceptual hash — в рамках одного скрапинга визуально идентичный, но по-другому захэшированный файл почти не встречается).
- Фильтр по минимальному разрешению — выключен по умолчанию, включается и настраивается через `catalog_scrape_config`, применяется одинаково ко всем источникам.
- `title` дизайна = alt-текст/подпись из источника (даёт осмысленный поиск по названию; иногда может быть мусорным/пустым).
- `isFeatured` у скачанных дизайнов всегда `false` — баннер «Популярные принты» отбирается автоматически по `useCount` (см. `GET /catalog/designs/popular`), без случайного попадания туда скачанных картинок с нулевым использованием.
- Старые 18 плейсхолдер-дизайнов без картинки (`seed.ts`) удаляются вместе с самим сидом — каталог полностью состоит из реальных картинок.

**Хранение:**

- Скачанные изображения хранятся на диске точки + в SQLite (`designs`) **навсегда** — без повторного скачивания и без TTL.

**Наполнение и подгрузка (киоск):**

- При старте point-server — фоновая job докачивает все 3 категории до минимального запаса (эагерное наполнение) сразу всеми включёнными источниками параллельно, не дожидаясь, пока пользователь реально откроет раздел.
- Страница раздела (`CategoryGallery`) переходит на инфинит-скролл: 12 карточек на экран + буфер +12, догрузка порциями по мере приближения к концу списка.
- Пока фоновая докачка не успела — в конце сетки показывается карточка-спиннер вместо резкого обрыва списка; если пользователь остаётся внизу списка, страница сама переопрашивает point-server раз в ~2.5 сек (без лишнего спама запросами), пока докачка идёт — карточки от более быстрых источников (Giphy) обычно появляются заметно раньше, чем успевает отработать Pinterest.
- Офлайн/нет новых картинок — по общему принципу fail-open проекта: показываем то, что уже в кеше, докачка просто не выполняется, ошибка пользователю не показывается.

**Поиск по названию:**

- Новый инпут на странице раздела (`CategoryGallery`).
- Поиск — бэкенд-запрос к point-server (`LIKE` по `title`) в пределах текущей категории по **всей** базе, а не просто фильтр по уже подгруженным на экране карточкам (иначе не найдёт то, что ещё не докачано в браузер).

**Настройки (панель оператора, point-server, не central-relay):**

- Вкладка «Дизайны» в сайдбаре оператора (`DesignsPanel.tsx`).
- Поля: включение/выключение источников Giphy/CleanPNG, минимальное разрешение (вкл/выкл + число), размер страницы/буфера, задержка между запросами, макс. запросов в час.
- Кнопка «Докачать сейчас» по каждой категории + статус последнего запуска (успех/ошибка, сколько скачано, дата) — из `catalog_scrape_state`; при ошибках нескольких источников в одном прогоне `lastError` показывает их все через «;».

**Изоляция картинок («Галерея» tab, `DesignsPanel.tsx`):**

- У каждой картинки — кнопка «Изолировать» рядом с «Удалить»: помечает `designs.isolated = true` (`PATCH /catalog/designs/:id/isolate`), не удаляя файл/запись. Картинка сохраняет свою обычную `category`, но пропадает и из галереи киоска, и из обычного просмотра по категории в панели оператора — изоляция это только фильтр, не отдельная запись в `designCategorySchema`.
- Отдельный фильтр-чип «Изолированные» рядом со списком категорий (не сама категория) показывает все изолированные картинки сразу по всем категориям; там же — кнопка «Вернуть» (снимает флаг) и «Удалить» (для окончательного удаления).
- `GET /catalog/designs` по умолчанию (без `?isolated=`) отдаёт только неизолированные — это касается и кисок-галереи (`CategoryGallery.tsx`), и баннера «Популярные принты»: изолированная картинка нигде не показывается покупателю без явного возврата оператором.

**Изменения в коде (ориентир):**

- `apps/point-server/src/modules/catalog/` — CRUD каталога, эндпоинт `?search=`/пагинации.
- `apps/point-server/src/modules/catalog-scraper/` — оркестрация (`scrapeService.ts`), настройки/статус/теги, фоновая job (запуск при старте + докачка по требованию); `sources/` — по одному модулю на источник (`pinterestSource.ts`, `giphySource.ts`, `cleanpngSource.ts`) за общим интерфейсом `ScraperSource`.
- `apps/point-server/src/db/schema.ts` — `designs.sourcePinId`/`designs.source`, `catalog_scrape_state`, `catalog_scrape_config` (включая `giphyEnabled`/`cleanpngEnabled`), `catalog_scrape_query_tags`.
- `apps/point-server/src/env.ts` — `GIPHY_API_KEY` (опционально, fail-open).
- `apps/point-server/package.json` + корневой `package.json` — `engines.node: ">=24"`, зависимости `pin-dl` и `playwright` (последний также используется напрямую для CleanPNG, не только как рантайм-зависимость `pin-dl`).
- `apps/kiosk-operator-app/src/routes/kiosk/CategoryGallery.tsx` — инфинит-скролл (12+12), карточка-спиннер, инпут поиска, переопрос во время докачки.
- `apps/kiosk-operator-app/src/routes/operator/DesignsPanel.tsx` — настройки каталога (источники, теги, статус) внутри вкладки «Дизайны».
- `apps/point-server/src/modules/catalog/seed.ts` — убрать плейсхолдер-заглушки.

## 7. Допущения

- Хостинг central-relay — любой VPS/PaaS с Postgres (Railway, Render, свой VPS).
- Видео-реклама хранится на central-relay (диск или S3) и скачивается точкой при обновлении. Каталог дизайнов — исключительно локальная сущность точки, без центрального «мастер-каталога».
- Оператор и клиент — один React-app с разными роутами.
- Обновление point-server на первых порах — вручную/по сигналу; полноценный авто-апдейтер — после пилота.
- Оплата в приложении не реализуется на первых этапах («Оплатите в кассу»).
- Печать — вручную оператором (загрузка PNG в софт принтера).

## 8. Риски и митигация

| Риск | Митигация |
|---|---|
| Лимиты Pollinations (rate limit, watermark) | Бесплатная регистрация; fallback на другие бесплатные API; кэш результатов |
| Первый запуск `@imgly/background-removal` медленный | Предзагрузка WASM/модели при старте киоска; self-host assets |
| Потеря интернета на точке | Fail-open: каталог и заказы работают локально; sync_queue |
| QR не работает без relay | Два режима: relay + own-WiFi; переключатель в админке |
| Два монитора / два окна Chrome | Отдельные профили Chrome, kiosk-режим, автозапуск скриптом |
| Скрапинг Pinterest вне их ToS, риск блокировки IP точки (Этап 3) | Настраиваемая задержка/лимит запросов в час, статус последнего запуска в настройках оператора, ручной контроль («Докачать сейчас») |
| `pin-dl` v0.1.0 — незрелая библиотека, может ломаться (Этап 3) | Изолировать вызов в отдельном scraper-модуле/`child_process`, чтобы падение скрапинга не роняло point-server |
| CleanPNG-источник (Этап 3) — тот же ToS-риск, что и Pinterest, плюс неопределённый статус прав на переразмещённые там картинки; Cloudflare обычно блокирует автоматическое скачивание | Источник опционален и по умолчанию просто ничего не находит при блокировке (fail-open) — не роняет прогон и не блокирует остальные источники; можно выключить в настройках оператора |
| Giphy-стикеры не всегда точно попадают в тематику раздела (мемы/аниме/игры) | Официальный API, минимальный риск блокировки — при плохом попадании в тему просто донастроить поисковые теги категории в панели оператора |
| Повышение Node.js до ≥24 и вес Playwright (~300MB) на мини-ПК точки (Этап 3) | Разовое обновление рантайма при подготовке образа точки (Этап 10) |
